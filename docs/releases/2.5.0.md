# bazis-mcp 2.5.0

## Features

- **The project of the conversation.** A client connects `uvx bazis-mcp` without any
  setting and asks for an application; the server creates it and goes on with the next
  changes in the same conversation (the project served changes without a restart):
  - `create_project(directory, description, name=None, frontend=True, language=None)`
    writes the skeleton in a new or empty directory (an absolute path; a temporary
    directory, the home directory and a directory inside another project are refused),
    installs `.venv` from PyPI, checks the project package and the language with the
    Python of the project, creates the database when PostgreSQL is reachable, chooses the
    ports and serves the project; a failed step leaves the directory as it was. A database
    of the name of the project that has data (such as that of another project in a
    directory of the same name) or cannot be opened is left as it is: the first missing or
    empty `<name>_2` ... `<name>_99` is created instead and set in `.env`, and `database`
    says so; an empty one of the name is kept, and a name set in the environment of the
    server is not changed. It returns
    the facts, the `rules` (`RULES`, with `FRONTEND_RULES` for a product with a frontend)
    and `next_steps`, the task of building the project. It reaches outside the machine
    (`openWorldHint`).
  - `use_project(directory)` serves an existing project (the directory of its
    `manage.py`) and returns its status and its `rules`; the project served changes only
    once its status is read, and the project of the command line keeps its `--settings`
    and `--python`. `create_project` and `use_project` run one call at a time.
  - `project_status()`: `directory`, `settings`, `python`, `frontend`, `ports` (null
    when `.bazis/ports.json` cannot be read), `database_name` (`BS_DATABASES__DEFAULT__NAME`
    of the environment of the server, else of `.env`, else of `project.env`) and
    `env_keys`, the names of the variables of
    `.env` read with python-dotenv (a value in quotes on several lines is not taken for
    variables, nor a line without `=` such as a pasted token or a line of a value on
    several lines without quotes, nor a name that is not an identifier), never their
    values; a `.env` that links outside the project is not read (`env_keys` null,
    `env_reason` says why).
  - `check_machine()`: the programs a project needs on this machine (`python`, `uv`,
    `node`, `postgresql`, `postgresql-service`, `redis`, `redis-service`, `gdal`,
    `gettext`), found without changing anything, each with `required_for`, `status`
    (`ok`, `missing`, `old`, `stopped`), `found`, the `install_command` of the package
    `manager` (Homebrew on macOS, apt on Debian and Ubuntu, from a closed table; none for
    the Python of a project, whose `.venv` is created again with a newer Python) and
    `needs_sudo`. The keg-only PostgreSQL of Homebrew (`postgresql@18`) is found in
    `<prefix>/opt/postgresql@18/bin`.
  - `install_tools(names, confirmed_by_user=False)` runs those commands only, as argv
    without a shell, once the user agrees: the client asks the user when it supports
    elicitation (on every protocol of the SDK), else `confirmed_by_user` must be true;
    without that nothing runs and `to_confirm` lists the commands. They run in the order
    of `check_machine`, a program before its server, whatever the order of `names`. The
    commands with sudo
    (apt), a Homebrew this user cannot run and a machine without a package manager are
    left to the user (`run_yourself`). It reaches outside the machine (`openWorldHint`).
  - The resources `bazis://rules` and `bazis://rules/frontend`, the prompts
    `new_project(description)` and `change_project(request)`, and the instructions of the
    server with the order of the work (the programs of the machine checked and installed
    once the user agrees, a new or an existing project, the rules, the
    project directory as the boundary of the files, `.env` never read, the summary).
  - `project.inside(path)`: a path of the project resolved with its symbolic links, or an
    error outside it; `project_status` reads `.env` only through it.
- **The work on the project for a client without a shell** (Claude Desktop): the commands,
  the servers, the packages and the files of the project served, never a command or a
  path of the caller outside them:
  - `add_packages(names)` adds the Bazis packages of the catalog (another name is refused)
    and those they require to `requirements.txt` with the version of the catalog as the
    minimum, installs `requirements-dev.txt` from PyPI into `.venv` and raises the
    minimums to the installed releases (`scaffold.raise_minimums`, also used by
    `create_venv`); when pip fails, or the call meanwhile, `requirements.txt` stays as it
    was. pip (also
    `run_command("pip")`) runs only with the Python of the project, `.venv` or `--python`,
    never with that of bazis-mcp (without one it is refused, with what to do), and only when
    every line of `requirements.txt` and `requirements-dev.txt` is a requirement of PyPI: a
    name with its extras and versions, and `-r requirements.txt` in
    `requirements-dev.txt`; a URL, `git+`, a path, the file of an archive (a name with an
    extension of an archive of pip, such as `demo-0.1-py3-none-any.whl` or
    `demo-0.1.tar.gz`, which pip installs as a local file), `-e`, another `-r`, `-c`,
    `--index-url`, `--extra-index-url`, `--find-links` or any other option of pip, and an
    environment marker are refused (local wheels are given to pip by `PIP_FIND_LINKS`).
  - `run_command(kind, args=[])` runs a command of a closed table as argv without a shell,
    in a new process group killed after 600 seconds (and when the call fails meanwhile,
    such as when the client is gone, or bazis-mcp ends, as the servers do), its progress
    reported every 5 seconds: `manage` (makemigrations, migrate, check, bazis_doctor, collectstatic,
    e2e_data, `bazis_front` and `bazis_messages` with their subcommands), `pytest`, `pip`
    (`install -r requirements-dev.txt` only), and in `frontend/` `npm` (`install` and `ci`
    without arguments; `run` of build, lint, test, e2e, format, with only the names of
    tests and a few options of test and e2e after `--`) and `npx` (`tsc --noEmit`,
    `playwright install chromium`, run as `npx --no` from `frontend/node_modules`, never
    downloaded; refused while they are not installed). npm and npx are found on the `PATH`
    (`npm.cmd` on Windows). An argument with a character of a shell, `..` or a path
    outside the project is refused, and so are the options of manage that choose other
    settings (`--settings`, `--pythonpath`, also abbreviated) and those of pytest that
    remove or write the paths they name or change its configuration, plugins or settings
    (`--basetemp`, `--junitxml`, `--log-file`, `--debug`, `--rootdir`, `--confcutdir`,
    `-c`, `-o`, `-p`, `--pyargs`, `--ds`, `--dc`, also in a group of letters, and
    `@<file>`).
    `E2E_PORT` (`.bazis/ports.json`) and `E2E_PASSWORD` (`.env`) are set by the server and
    the password is hidden in the output, of which the last 10,000 bytes are returned.
  - `start_server(which)`, `stop_server(which)` and `server_logs(which, lines=100)`: the
    backend (uvicorn) and the dev server of the frontend (vite, `--strictPort`) on the
    ports of `.bazis/ports.json`, in the background with their log in
    `.bazis/logs/<which>.log`; refused when the port is taken by another process; stopped
    by process group (SIGTERM, then SIGKILL after 10 seconds), also when bazis-mcp ends,
    by itself or by SIGTERM or SIGINT: then the servers and the commands that run
    (`run_command`, `add_packages`) are stopped together, SIGTERM to every group before
    the wait, and a signal that comes meanwhile does not end bazis-mcp before they are;
    a command or a server started meanwhile is refused.
  - `read_file(path, offset=0, limit=None)`, `write_file(path, content)` and
    `list_files(subdir='')` within the project directory (`project.inside`): `.env` is
    never read nor written, `.venv/`, `.git/`, `contract/` and the `generated/`
    directories are never written (these names in any case, `.ENV` too, and a file that is
    the same as one of them, such as a hard link to `.env`); the sizes are bounded (a file
    read fits in a result, a longer one is read in parts: its lines from `offset`, at
    most `limit`, with `next_offset` the line to read next; a file written has at most 1,000,000 bytes, a listing at most 400 entries).
  - `delete_file(path)` deletes a file of the project, such as one an agent no longer
    needs: a symbolic link is deleted itself, never what it links to (which is in the
    project too); a directory, what `write_file` never writes (`.env` also through a
    link, `.venv/`, `.git/`, `contract/`, a `generated/` directory) and `manage.py` and
    `requirements*.txt` of the project directory (in any case) are refused.
  - The instructions of the server set these boundaries: the files in the project, the
    commands only with `run_command`, the servers with `start_server` and `stop_server`,
    the packages with `add_packages`. They keep an agent from mistakes and misuse, not a
    boundary against the code of the project: the commands run it (the settings, the
    tests and their plugins, the scripts of `package.json`, the install scripts of the
    packages) with the rights of the user. `RULES` says that an agent without a shell runs its
    commands with these tools; the prompts `new_project`, `add_package` and
    `build_frontend` name them.
- `scaffold.valid_package_name(name, python)` checks the modules a project package must
  not hide in the Python asked (`python -I`), by default the Python running it: in a
  server without Django, `create_project` checks the name again with the Python of the
  project after `.venv`, so `django` or `bazis` never become the project package.

- The skeleton of a new project, the rules of Bazis for an agent and its tasks are moved
  here from bazis-cli, which builds its commands on them: `bazis.contrib.mcp.scaffold`
  (the files of a project, `.venv` with its minimums raised to the installed releases,
  the database, `.bazis/ports.json`, the check of Node.js), `bazis.contrib.mcp.rules`
  (`RULES`, `FRONTEND_RULES`, with the same texts) and `bazis.contrib.mcp.prompts` (the
  tasks of a new project, of a package added and of a change, and the steps of a
  frontend). Nothing of them imports Django: `scaffold.product_language(code, python)`
  reads the language of Django of a code with a Python that has Django, such as that of
  the project, and `scaffold.set_language(directory, language)` writes it in
  `project.env` of a skeleton, which `write_files` writes in English.

## Changes

- bazis-mcp depends on python-dotenv (the names of the variables of `.env`) and on anyio
  (the progress of `run_command`, already a dependency of mcp).
- The `.env` of a new project has `E2E_PASSWORD`, a random password of the test users of
  the end-to-end tests (`manage.py e2e_data` reads it through the settings, `run_command`
  gives it to `npm run e2e`).
- bazis-mcp no longer depends on bazis: the server never imports the core, it runs the
  project tools with the Python of the project (`--python`, else `.venv`), so
  `uvx bazis-mcp` installs only the server. bazis is in the extra `test` (the sample
  project and the skeleton of the tests). A server run without a Python of the project
  needs the packages of the project in its own Python, as before.
- The skeleton of a new project requires the latest releases, whose guides the catalog
  describes: bazis 2.16.0 (`scaffold.REQUIREMENTS`, also in the extra `test`) and
  bazis-test-utils 2.5.2 (`scaffold.REQUIREMENTS_DEV`).

## Breaking changes

- A server started without `--project-dir` in a directory without `manage.py` serves no
  project: every tool but `create_project` and `use_project` answers "No project: call
  create_project or use_project" (before, the current directory was taken as the project,
  and the catalog tools read the packages of the Python of the server). Pass
  `--project-dir` for a project whose `manage.py` is elsewhere. The tools are no longer
  all read-only: `create_project`, `use_project`, `install_tools`, `add_packages`,
  `run_command`, `start_server`, `stop_server`, `write_file` and `delete_file` are not. A client that
  allows every tool of the server without asking now allows these too.
